# 翻译吞吐观测与对照实施

日期：2026-09-14。本文对应翻译性能计划中的最高优先级：确认游戏运行卡顿是否来自大量 `replace` 请求，并用同一语料比较批大小。

## 已实现

每次运行创建独立的有界指标收集器，停止、续译和迟到线程不会串入其他运行。请求统计区分逻辑请求入口、provider 调用次数、可观测 HTTP 尝试次数、应用退避等待和 provider 总耗时。SDK 内部重试如果没有 HTTP 钩子只计入 provider 耗时，不虚构 HTTP 次数。

调度统计包括并发槽等待、限速等待、线程池排队、任务构造、解析校验和缓存保存。样本最多保留 2,048 个，报告不包含提示词、译文、密钥或文件路径。有效速度只计算本轮新完成、状态为 `TRANSLATED`、译文非空且不同于原文的唯一条目，单位为条/分钟。

监控页显示有效速度和请求 P95，完整明细写入输出目录 `.renpybox_metrics/translation-throughput-<session>.json`。并发任务的累计耗时会重叠，不能把各阶段耗时相加当作墙钟时间。

## 如何复跑

使用 `scripts/benchmark_translation_throughput.py`，默认 dry-run 只验证分块；`--execute` 才会调用真实接口。固定同一语料、平台、并发、超时、思考挡位和校验规则，依次比较 legacy10、source1024 和 balanced20，每档至少三次。比较 `effective_items_per_minute`、请求 P50/P95、重试等待、失败/回退计数和 token 用量；仅在 HTTP 观测完整时使用 HTTP 尝试数。

当前仓库没有代表性游戏输入，也没有可安全调用的真实 API 运行记录，因此本轮不提供伪造的线上速度结论。下一步仍需固定游戏副本和真实接口完成对照，再决定默认批大小与并发。

统一 HTTP 层限流、`Retry-After`、各 SDK transport 钩子和 DeepLX 单条请求额度属于下一项 P1；复杂 Hook 覆盖证据属于另一项 P1。
