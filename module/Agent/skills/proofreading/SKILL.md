# 译文质量检查

## 先分类再动手

拿到一批译文，先判断问题属于哪一类，不同类的处理方式完全不同：

| 类别 | 表现 | 能否自动修 |
|---|---|---|
| 结构性 | 标签丢失、占位符损坏、换行丢失 | 可以按规则修 |
| 漏译 | 译文等于原文、译文为空 | 需要重译 |
| 术语不一致 | 同一个词多种译法 | 需要用户拍板 |
| 风格问题 | 机翻腔、语气生硬、口语变书面 | 需要重译，不可机械替换 |
| 长度问题 | 译文明显长于原文 | 需要精简 |

## 结构性问题的检查点

1. `[...]` 插值数量和内容是否与原文一致
2. `{...}` 标签是否成对、名字是否一致
3. 换行数是否一致
4. 英文引号是否未转义
5. 原文为空时译文是否也为空

这几条可以用脚本或工具批量发现，`scan_script_errors` 能覆盖语法层面的部分。

## 漏译的识别

- 译文与原文完全相同（注意排除本来就不该译的：人名缩写、音效拟声、代码串）
- 译文为空但原文非空
- 译文只是原文的机械转写

发现漏译时报告条数和样例，不要逐条念给用户。

## 机翻腔的典型特征

- "的" 字堆叠："这是一个非常重要的决定的事情"
- 被动语态滥用："这个问题被解决了由他"
- 代词冗余："他拿起了他的剑" → "他拔剑"
- 连接词直译："然而，因此，此外" 出现在口语里
- 定语过长，一句话套三层

修法是重写，不是替换词汇。

## 语气一致性

### 角色声音

同一个角色在不同场景的说话方式应该一致。傲娇角色不会忽然用敬语，粗人不会忽然文绉绉。

### 场景语域

战斗场景用短句，日常场景可以长一些，系统提示用书面语。不要全篇一个腔调。

## 长度溢出

中文通常比英文短，比日文短，但也有例外：
- 片假名外来语译成中文往往会变长
- 英文缩写展开成中文会变长
- 定语从句译成中文前置定语会变长

文本框有固定宽度，超过就溢出。判断标准：译文长度超过原文 1.3 倍时检查是否必要。

## 报告方式

不要罗列所有问题。按这个格式给结论：

```
检查范围：<文件数> 个文件，<条数> 条译文
结构性问题：<n> 条（可自动修）
漏译：<n> 条
术语不一致：<n> 处（需用户决定）
风格问题：<n> 条（需重译）

样例：
- <文件>:<行> 原文... → 译文... 问题类型
```

然后问用户先修哪一类。全量重译成本很高，通常不值得。

## 不要做的事

- 不要在没有用户确认时批量覆盖译文
- 不要把风格问题当结构性问题"修"——机械替换只会更糟
- 不要声称检查过没看过的文件
